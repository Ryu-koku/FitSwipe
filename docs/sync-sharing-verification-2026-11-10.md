# FitSwipe 同期・共有の検証（2026-11-10）

README.md「画面と操作」「バックアップ・体組成」を基準とした。既存の未コミット変更は保持し、認証・認可・入力検証および別担当の変更には手を加えていない。Worker の同期・共有の実体は `personal-sync.mjs` / `room-comparison.mjs` に分離されているため、本担当のサーバー修正は `room-comparison.mjs` のみ。コミット、デプロイ、本番 D1 操作は実施していない。

## 修正した問題

### 1. 保存失敗でも画面上の記録・送信待ち・ACKが進む

- **重大度:** 高（記録と永続データの不一致、未保存データの送信、ACK済みと誤認）。
- **再現条件:** 通常の `persist` または push 後の ACK 保存でストレージ書き込みを失敗させる。
- **原因:** `mobile/src/context.tsx:104` / `:136` の旧処理が、`saveState` 成功前に `current.current` と React state を更新していた。ACK保存が失敗してもメモリ上では pending が空になった。
- **修正内容:** 更新関数の評価から永続化・公開までを同じ直列キューへ移動。保存が成功した場合のみメモリと画面を更新する。失敗した ACK は pending に残し、同じ mutationId で再送できる。
- **追加テスト:** `mobile/test/import-persistence.test.cjs:152` の通常保存失敗・再試行・同時編集、`:168` の ACK 保存失敗。修正前はいずれも失敗（元 state と一致しない / pending が `[]`）、修正後は成功。

### 2. 先行保存中の取り込み・ログアウトが古い記録を使う

- **重大度:** 高（直前の編集や送信待ちが取り込みで消失し、ログアウト時のアーカイブから欠落）。
- **再現条件:** 通常編集の保存を保留したまま CSV 取り込み、または期限切れセッションからログアウトする。
- **原因:** `mobile/src/context.tsx:356` の取り込みが先行 writer を待たず旧 state から次状態を作成し、`:300` のログアウトが先行保存前の state をアーカイブしていた。
- **修正内容:** 取り込みも共通の保存キューで最新確定状態から評価する。同期・プロフィール・ログイン・ログアウト・削除・保管データ交換は先行 writer が完了してから状態を参照する。
- **追加テスト:** `mobile/test/import-persistence.test.cjs:180`（編集中の取り込み）、`:194`（編集中の期限切れログアウト）。キュー導入後の未対策状態では両方 `heightCm: undefined` となる失敗を確認し、対策後は 171 と対応する pending が保持される。

### 3. 同時 outbox 再送で同じ投稿を重複送信する

- **重大度:** 中（余分な送信、通信量・レート制限、ACK処理の競合）。
- **再現条件:** 同じ `getState` を利用する二つの画面処理から `flushPendingPosts` を、最初の POST 完了前に呼ぶ。
- **原因:** `mobile/src/rooms.ts:248` の旧処理に実行中フラッシュの共有がなく、両方が同じ先頭投稿を選ぶ。
- **修正内容:** `getState` ごとに WeakMap で実行中 Promise を共有し、同時フラッシュをまとめる。サーバーの既存の投稿ID重複排除も維持。
- **追加テスト:** `mobile/test/outbox.test.cjs:96`。修正前の送信回数 2、修正後 1。

### 4. 旧アカウントの POST 応答が新アカウントの outbox を削除する

- **重大度:** 高（別アカウントの未送信記録の消失）。
- **再現条件:** A の POST 中に B の状態へ切り替わり、B の outbox に同じ roomId/clientId がある状態で A の成功応答が返る。保管状態や同一端末ID由来の投稿を想定した状態組み合わせ。
- **原因:** `mobile/src/rooms.ts:265` の旧 ACK 削除が現在のアカウントを確認せず roomId/clientId だけで pending を取り除いていた。
- **修正内容:** フラッシュ開始時のアカウントIDとトークンを固定し、各反復と保存キュー内の削除時にも一致を確認する。別アカウントのキューは保持して旧処理を終了する。
- **追加テスト:** `mobile/test/outbox.test.cjs:84`。修正前は B の pending が 0 件、修正後は 1 件のまま。

### 5. 保存コミット後の不要チャンク削除失敗を保存失敗として返す

- **重大度:** 高（保存成功を失敗扱いし、再取り込みやメモリ・ディスクの不一致を誘発）。
- **再現条件:** 新しい manifest の保存を成功させ、その後の旧チャンク削除だけ失敗させる。
- **原因:** `mobile/src/storage.ts:121` で manifest を確定した後の `multiRemove` 例外が呼び出し元まで伝播。読み込み時の不要チャンク掃除にも同様の問題があった。
- **修正内容:** manifest 書き込みを確定点とし、以後の掃除と読み込み時の掃除は失敗を許容する。完全な確定世代は読み出せ、不要チャンクは後続ロードで再掃除する。manifest 自体の失敗は従来どおり reject し旧世代を保持する。
- **追加テスト:** `mobile/test/cloud-storage.test.cjs:190`。修正前は「disk full」で reject、修正後は保存成功として解決し、掃除失敗が継続していても新しい身長 180 を読み出せる。

### 6. 個人同期UUIDへの移行で自動共有が二重化し、削除後も旧コピーが残る

- **重大度:** 高（二重集計、削除反映漏れ）。
- **再現条件:** 同意済みルームに端末IDの自動共有があり、Google連携後に同じセッションを同期UUID＋`legacyClientId`で自動共有する。
- **原因:** `rooms-server/cloudflare/room-comparison.mjs:76` の旧保存が `(room_id,user_id,client_id)` 単位の upsert のみで、既存の旧ID自動コピーを残した。比較ビューは手動共有との重複だけを排除するので自動同士は二重集計された。
- **修正内容:** UUIDコピーの保存と旧IDコピーの削除を D1 の同一 batch で実施。上限1,000件でも旧コピーの置換を許可する。移行済み旧IDの遅延再送は INSERT 内の条件で抑止し、旧コピーが復活しない。既存の手動共有と同意確認は保持する。
- **追加テスト:** `rooms-server/cloudflare/test/sync-sharing-verification.test.mjs:20`。修正前は投稿数・セット数 2、修正後は 1。UUID再送、旧ID遅延再送、UUID削除後の0件も検証。`:98` では上限時の置換と、削除途中の注入エラーで全体がロールバックして元の1,000件を保持することを検証。

## 再現済み・方針判断待ち（未修正）

### 90日を超える ACK 未保存の再送が、別端末の新しい変更を上書きする

- **重大度:** 高（新しい個人記録・削除状態・設定の消失／巻き戻り）。
- **再現条件:** 端末Aの mutation はサーバーへ到達したが、応答切断または端末保存失敗で ACK が pending に反映されない。その後Aが90日超オフラインの間に端末Bが同じ記録を更新する。cron がAの receipt を削除した後、Aが旧 mutation を再送する。
- **原因:** `rooms-server/cloudflare/personal-sync.mjs:68` / `:73` が90日で receipt を削除する一方、同じファイルの `pushChanges` は receipt の存在だけで旧 mutation を判定する。端末 outbox 自体に90日の期限はない。`0006_session_cleanup.sql` 以前の receipt は `created_at=0` のため初回 cron で削除される点も確認した。
- **実測:** `sync-sharing-verification.test.mjs:83` で作成日時を91日前にして cron →再送。期待する新値 `light` が旧値 `dark` に戻り、revision も2から3へ進む。
- **対応:** コーディネーターへ ask し、保持量・Play提出資料・プライバシー説明への影響があるため「再現と報告のみ」の指示を受けた。保持期限は変更していない。テストは `todo` として実行し、既知の失敗を表示しつつ全体の終了コードは0とする。
- **代替案と代償:**
  1. **90日保持を継続し、期限超mutationを拒否する。** サーバーが信頼できる発行時刻／端末世代を必要とする。端末は最新状態を取得し、ユーザーの未送信編集を再適用する仕組みが必要。時計ずれ・旧クライアント互換・同じ編集の再適用による復活の扱いを決める必要がある。
  2. **レコード版番号による条件付き更新。** 期待 revision と現在 revision が違う更新を拒否し、競合解決する。保持期間を変えずに古い上書きを防げるが、API・端末outbox形式の変更、旧クライアントの扱い、競合UIが必要。
  3. **receipt をアカウント削除まで保持。** 現行クライアントと互換のまま任意期間の再送を冪等にできるが、mutation数に比例して保存量が増え、保持期間の方針・説明の変更が必要。

## その他の確認結果

- 新規テストで sync batch の2件目へのエラー注入を実施し、revision・record・receipt がすべてロールバックすること、同一mutation再送と新しい更新後の旧mutation重複配送（receipt保持中）が冪等であることを確認。
- `0001` から `0009` の各適用済み途中版を作り、残りを順に適用。すべて同じ最終スキーマとなり、既存ユーザーと `0002` 以降の同期record/revision/receiptが保持され、`foreign_key_check` は空。再現できる適用順の穴や Worker 期待列の欠落は見つからず、マイグレーション変更は不要。
- 既存の mobile 自動共有テストで、未同意時の0件、同意月初の日本時間境界、未来・未完了記録の除外、当月＋過去11か月、セット除去・修正・削除、他端末の未取得記録を取り下げないこと、通信失敗／部分失敗／容量超過の再試行を確認。
- 実際の Worker をローカルHTTP経由で呼ぶ既存統合テストで、同意以前の月の拒否、停止による自動コピーのみの削除と手動共有の保持、ランキング・比較ページングを確認。
- 体組成の同期は個別settingレコードで既存テストを通過し、自動共有の snapshot は種目・重量・回数・日時で構成される。体重・体脂肪率・身長を追加する変更は行っていない。

## 未確認の懸念

- アカウント削除のサーバー成功後に端末保存が失敗した場合の再試行導線。現在の記録自体は保持されるが、失効済み認証状態からの復旧可否について本担当では再現テストを作成していない。
- 自動共有の一覧取得後に別端末が編集・同意の停止と再開を同時実行する、実環境のリクエスト順序の全組み合わせ。本検証はD1相当のトランザクションと明示的に注入した競合を対象とし、分散システム全体の網羅的証明ではない。

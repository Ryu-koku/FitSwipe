# ルーム機能の要件レビューと決定事項

回答元: `akapen/room-requirements-01.html.answer.txt`（第1稿、4問すべてA、追加コメントなし）。
本書は要件レビューの成果物。後続の「実装して」の依頼により、確定した4項目をアプリとCloudflare／セルフホストの両サーバーへ実装。配信・実機検証は未実施。

## 回答で確定した方針

1. **招待**：知人向けの招待コードによる即参加を維持する。作成者によるコード更新と除名を追加する。参加承認制にはしない。意図しない参加者が、対処まで既存の共有記録を閲覧できる可能性は残る。
2. **作成者の通常退出**：「引継いで退出」を追加する。参加が最も早い残存メンバーへ操作権を移し、仲間の記録を残す。残存メンバーがいなければルームを削除する。全体削除は別操作として区別する。
3. **自動共有の保存期間**：当月と過去11か月を保存する。1年以上前の自動共有を取り下げる。端末の個人記録と以前の手動共有は対象外。現在の1万件制限はこの方針だけでは解決しないため、期間内の容量設計も必要。
4. **競争設定**：新規作成時は「競い合わない」を初期選択にする。作成前に変更可能とし、既存ルームと集計指標は変更しない。

## 実装時に確認する条件

- 招待コードの更新後は旧コードで参加できないこと。管理操作を作成者だけに許可し、除名後の閲覧・送信を拒否すること。
- 引継ぎと退出でルームの管理者が不在にならず、本人の共有データだけが取り下げられること。全体削除と取り違えない説明を設けること。
- 保存期間を過ぎた自動共有が、古い端末の再送で復活しないこと。個人記録と手動共有を巻き込まないこと。
- 非競争の初期値を新規作成に限定し、競争を選んだ場合は選択どおり保存すること。

上記は確定した方針から導かれる検証条件。再参加の制限方法、削除処理の実行時刻、具体的な容量上限などの実装詳細を、この文書で新たに確定したものではない。

## 優先順位

共有前の説明・アクセス管理・退出時の影響を先に整える。次に一部送信失敗の切り離しと保存容量の設計を行い、詳細の探しやすさ・状態表示・接続先との対応関係を確認する。以下の指摘は根拠と改善案であり、4問以外の仕様がすべて承認されたことを意味しない。

対象は現在のExpoアプリとCloudflare版サーバー。既存の承認記録 docs/ui-refresh-decisions.md を基準に、要件とコードを読んで照合した。稼働中サーバー・実機の動作は未確認。以下は不具合の再現結果ではなく、確認できた実装上の事実と要件への提案である。実装変更は含まない。

維持する要件：ルーム単位の同意、同意月以降の完了記録、編集・削除の反映、日本時間の月次セット数、同順位、左右ペアを1セット、手動共有の別管理。これらは今回の選択肢で再決定しない。

## 多角的レビューと完成時に満たす条件案

### 1. [高] 同意・プライバシー — 開始前に共有範囲を理解できない

現状・影響：開始操作は直ちに有効化する。月初からの遡及共有と日時の共有を開始前に説明する要件が必要。

根拠：mobile/src/app/rooms.tsx:53,69,99 / docs/ui-refresh-decisions.md:10

完成時に満たす条件案：有効化前に対象ルーム・閲覧者・対象期間・共有項目・停止の効果を表示し、取消時は一件も送らない。

### 2. [高] 招待・アクセス管理 — コード流出後の対処が足りない

現状・影響：全メンバーへコードを返し、コード一致で即参加する。調査したAPIに招待失効・除名・承認はない。

根拠：rooms-server/cloudflare/worker.mjs:158,189,369

完成時に満たす条件案：問1で運用範囲を決める。新参加者は既存の共有記録も読めることを同意説明に含める。

### 3. [高] 削除・管理者 — 作成者だけ、ルームを残して退出できない

現状・影響：通常の退出APIでは作成者なら全体削除。アカウント削除では他のメンバーへ引継ぐため、操作による結果の差が大きい。

根拠：rooms-server/cloudflare/worker.mjs:282,354 / mobile/src/app/rooms.tsx:71

完成時に満たす条件案：問2で方針を決める。本人のデータと仲間のデータへの影響を確認画面に明記する。

### 4. [高] 通信・継続利用 — 一つの失敗が別ルームの共有を止める

現状・影響：順番に送信し、個別の失敗を処理せず共有処理全体を中断する。上限到達など恒常的な失敗があると後続へ進めない。

根拠：mobile/src/automatic-sharing.ts:56,73

完成時に満たす条件案：失敗した記録・ルームを識別し、他ルームの送信を継続する。未送信を保全し、再試行可能な失敗と修正が必要な失敗を区別する。

### 5. [高] 保存容量・運用 — 1万件到達後の継続方針がない

現状・影響：自動共有は削除済みとして残しているデータも含めて数える。100人が毎日1件なら約100日で1万件に到達する計算。実測ではない。

根拠：rooms-server/cloudflare/room-comparison.mjs:57,69

完成時に満たす条件案：問3で保存期間を決める。アプリが普段読み書きする保存先と復旧用コピーの消去期限、容量通知、削除後の古い再送防止を設計する。

### 6. [中] 集計・公平性 — 月境界は開始日時で決まる

現状・影響：完了したトレーニングを開始日時の月に集計する。月末開始・翌月終了は前月分。左右の片側だけは0、同数は同順位。

根拠：rooms-server/cloudflare/room-comparison.mjs:17 / mobile/src/automatic-sharing.ts:11

完成時に満たす条件案：開始月・日本時間・左右の数え方を利用者向けに明文化する。セット数は記録量の比較であり、筋力や努力の優劣を示さない。

### 7. [中] 継続の動機・競争 — 非競争でもセット数は見える

現状・影響：非競争は名前順でセット数を表示。競争の有無は順位の有無で、他人の数字を見ない機能ではない。

根拠：mobile/src/components/RoomComparisonChart.tsx:52

完成時に満たす条件案：現在の意味を説明する。指標の変更や新機能追加は今回確定しない。競争の初期値は問4で選ぶ。

### 8. [中] 詳細の見つけやすさ — 個人詳細を全員分のページから探す

現状・影響：全メンバーの記録をまとめて50件ずつ取得してから選択した人だけに絞るため、目的の人の記録に何度も追加読込が必要になり得る。

根拠：rooms-server/cloudflare/room-comparison.mjs:82 / mobile/src/app/rooms.tsx:149

完成時に満たす条件案：集計に数値がある人の詳細へ直接到達できることを要件化。未読込と記録なしを区別する。

### 9. [中] 状態・読み上げなどへの対応 — 0セットだけでは共有状態を説明できない

現状・影響：全メンバーを0も含めて集計する。他人の共有OFFと記録なしを区別する情報は比較結果にない。読み上げ名と動きの抑制対応はある。

根拠：rooms-server/cloudflare/room-comparison.mjs:33 / mobile/src/components/RoomComparisonChart.tsx:16,27

完成時に満たす条件案：共有OFF・未同期・記録なしを同じ意味で説明しない。共有状態を他人へ公開するかは追加設計が必要。大きな文字・100人・同名・読み上げは実機確認対象。

### 10. [中] 接続先との対応関係・保守 — 二つのサーバーで説明と能力が異なる

現状・影響：自分で運営するサーバーの文書は手動共有中心。現在のアプリは比較APIの404を非対応扱いにする。自動共有前提のREADMEとの適用範囲が曖昧。

根拠：rooms-server/README.md:3 / mobile/src/use-rooms.ts:35 / rooms-server/cloudflare/README.md:33

完成時に満たす条件案：サーバーごとの対応機能表を置き、未対応の共有操作を利用者に提示しない。配信前に必要なデータベース更新を済ませた構成で確認する。

### 11. [中] 復元・複数端末 — 共有と個人同期の境界を明文化したい

現状・影響：別端末でまだ取得していない記録を誤削除しない仕組みはある。古い端末からの更新・停止と送信の同時実行は追加の完成時に満たす条件が必要。

根拠：mobile/src/automatic-sharing.ts:26 / rooms-server/cloudflare/room-comparison.mjs:60

完成時に満たす条件案：二端末同時編集、共有停止中の送信、退出後の再送、月を跨いだ再開でデータが復活・重複しないことを検証する。

## 検証の範囲

既存テストに同意・重複防止・左右集計・取り下げ・通信失敗・別端末の未取得記録保護の検証があることを確認した（mobile/test/automatic-sharing.test.cjs:15、rooms-server/cloudflare/test/room-comparison.test.mjs:18）。今回は実行していない。追加検証の優先順は、同意前の送信禁止 → 共有停止と送信の同時実行 → 一部失敗時の継続 → 保存上限 → 月境界・100人・実機読み上げ。以下の4問は運用上の利点と代償だけを確認する。
